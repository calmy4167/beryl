## 2. 主审先行发现

- 原始主档案的价值是完整世界观和长期领域语言；首版产品不应把这套复杂度同时交给用户。
- 当前规范已经明确 MVP 不做完整关系协作、旧工具模块、强制五行和实时双向同步。
- 当前 AppShell 却默认暴露上述大部分能力，产品承诺与信息架构相反。
- 当前代码的测试和基础设施进展快于 UI 收敛；“能力存在”被误当成“用户路径成熟”。
- 文档数量本身不是问题，问题是缺少唯一入口和状态标签，导致历史设计、未来愿景和当前验收混在一起。

## 3. 独立评审意见

### 产品策略席

结论：Calmy 应停止增加功能，把 Beryl 工具箱、Case 工作台和 Matter OS 的三代叠加态收敛为一个产品。差异化不在五行、图谱或 Obsidian，而在“减法式 Today + 非评判的真实记录”。

主要意见：

- 目标用户聚焦长期学习、职业转型、低承载状态和反复中断/恢复者，而不是泛化到情侣、夫妻和家庭。
- 立即合并 `Case → Matter`、`Task → Action`、`Inbox/Home 快速记录 → Capture`；旧 Diary、Moments、Posts 未来只作为 Record 模板或视图。
- 可见产品建议缩减约 60%；Stable ID、revision、IndexedDB、冲突历史和 Open Format 保留在可靠底座。
- 主张将 Review 与 Calendar 合并到 History；会议最终保留独立 Review 入口做首版验证，因为它是核心闭环的必要动作。若试点显示用户更自然地从历史进入复盘，再合并为 History。
- 建议指标增加 Capture P50 ≤ 10 秒、首次下一步 P50 ≤ 60 秒、核心导航不超过 4 个、AI 未确认写入与静默冲突均为 0。

对会议的关键质询：Case 是否有任何无法映射到 Matter 的语义；没有 AI 时核心闭环能否成立；哪一类目标用户已有连续两周的行为证据。

### UX / UI 席

结论：这不是视觉换肤问题，而是产品模型收口问题。用户心智应固定为“Person 是上下文，Matter 是现实主体，Action 是下一步，Record 是证据；Cycle / Stage 按需展开”。

主要发现：

- 当前桌面一级导航达到 11 个入口并叠加工具箱；Home/Today、Case/Matter、Capture/inbox 互相争夺职责。
- Today 同时铺开晨间定向、白天执行与晚间复盘，形成 8 个主要区块和大量输入；应按时段和完成状态渐进披露。
- People 当前更像关系数据库管理表单；Vault 冲突、revision、mutation log、Asset hash/MIME 等运维信息混入用户页面。
- 浅色辅助文字对比度约 2.62:1，存在 9–10px 字号、20px 勾选和 34–36px 移动控件，且缺少 reduced-motion 处理。
- local-first 的核心界面仍加载 Google Fonts 和外部 Quote 内容，应移除核心路径的外部依赖。

UX 席建议保留 Home、Today、Matters、People、Library 五个一级入口。会议裁决不采纳：Home 与 Today 合并，People / Library 服从 MVP 边界降级；保留其页面设计意见作为未来二级视图规范。

### 工程与数据视角（主审补位）

结论：基础设施能力已经超过首版产品需要，但真实用户写入路径没有同步收敛。代码中八个领域已有异步 Repository 入口，主要 Vue 视图对 `AsyncRepository/asyncRepository` 的直接使用数量仍为 0；页面继续编排同步仓储、命令和跨实体写入。

P0 意见：

- 先定义 5 个异步应用用例，不再让页面直接拼接领域写入。
- Case/Matter、Task/Action、inbox/Capture 必须选定唯一新写入模型，旧模型只读兼容。
- 把“本地已保存”“等待同步”“同步失败”“冲突”拆成不同状态。
- Companion Bridge 协议和模拟测试不能替代真实插件与跨设备联调证据。
- 品牌 UI 可以先迁移到 Calmy，但 `b_*`/`beryl-*` 存储键必须兼容读取和渐进迁移，不能直接全量改名。

### 质量、隐私与反方视角（主审补位）

最可能导致用户放弃的 10 个原因：

1. 不知道应该从 Home、Today、Cases 还是 Matters 开始。
2. 为简单记录先学习 Matter、Cycle、Stage、Seed、Trajectory 等术语。
3. Capture 后立即被迫分类或处理建议。
4. Today 首屏表单过多，低承载时反而增加压力。
5. Beryl/Calmy、Case/Matter、收集/inbox 的混合文案削弱信任。
6. 情侣/家庭场景看似共享，但真实数据隔离和协作承诺不清。
7. 本地保存与云端同步被混为一谈，用户无法判断数据是否安全。
8. 低对比小字、过小触控目标和长表单影响移动端与可访问性。
9. 外部字体/Quote 请求与 local-first、隐私和离线承诺冲突。
10. 产品显示很多高级能力，却不能稳定完成最基本的两周日常闭环。

隐私与发布意见：

- AI 默认只处理最小必要字段；发送到外部前展示范围，原文、关系边界和健康/心理记录默认不外发。
- Shared Space 和家庭场景在权限、撤回、审计和删除传播完成前不得进入默认产品。
- 导出文件要明确是否含私密记录、附件和身份信息；提供加密或风险提示。
- 自动化测试不能证明真实移动设备、读屏、用户理解、跨设备 Bridge 或长期数据恢复。
- P0 发布阻断：静默丢失/覆盖、双事实源新增、AI 未确认写入、共享越权、导出不可恢复、核心流程必须依赖网络。

建议试点为 8–12 位目标用户、2–4 周；首周无引导完成核心闭环，后续访谈聚焦“下一步是否更清楚”和“是否更少被系统评判”。任何 P0 数据/隐私问题立即 No-Go；达到路线图中的闭环和可理解性条件后才进入受控扩展。

## 4. 已形成的共识

1. 核心哲学保留，但从“首屏模型”变为“系统行为原则”。
2. 主导航必须减到四个核心目的地，搜索和上下文能力进入 More。
3. Today 取代 Home 成为产品中心；Cases 合并到 Matters；inbox 合并到 Capture。
4. 关系、Graph、旧模块和高级理论视图不得继续占用 MVP 默认路径。
5. 数据层的下一步不是增加更多仓储，而是让真实视图统一走异步应用用例。
6. 发布判断必须同时包含用户闭环、数据可靠性、可访问性和人工试点。

## 5. 分歧与裁决

| 分歧 | 裁决 |
|---|---|
| 是否删除超出 MVP 的现有代码 | 暂不删除；默认隐藏、停止新写入，并制定迁移/退场策略 |
| People 是否保留一级导航 | 否；首版只作为 Matter 上下文和 More 二级入口 |
| Library 是否是核心页 | 否；搜索与可携带数据是能力，Library 是二级视图 |
| 是否现在深化 Graph 和五行可视化 | 否；先验证核心闭环，只有真实需求才进入受控扩展 |
| 是否可凭 46/233 测试结果发布 | 否；还需真实视图持久化、人工无障碍和用户试点证据 |
| Beryl 品牌和存储键是否一起立即替换 | UI 品牌先统一；存储键采用兼容读取、迁移写入，不能粗暴改名 |

## 6. 最终决议

- 采用[产品重设计](PRODUCT_REDESIGN_2026-08-22.md)与[UI / UX 重设计](UX_UI_REDESIGN_2026-08-22.md)作为当前产品基线。
- 采用[工程评审](ENGINEERING_REVIEW_2026-08-22.md)中的停止线，暂停新增模块。
- 按[路线图与验收](ROADMAP_AND_ACCEPTANCE_2026-08-22.md)先完成阶段 0–2，再决定是否进入小规模试点。
- 所有旧文档保留，通过[文档登记册](DOCUMENT_REGISTER.md)管理权威性，不再依靠文件名或日期猜测状态。

## 7. 实施跟进（2026-08-22）

本轮已完成产品壳收敛：默认入口改为 Today，主导航固定为 Today、Capture、Matters、Review，Home、Cases、inbox、Graph、场景和旧工具箱不再占用默认路径；Calmy 品牌已进入主界面，旧路由与 `b_*` / `beryl-*` 存储键保留兼容。桌面 AppShell 进一步形成四边工作台：左侧导航、顶部上下文、右侧快捷动作、底部命令条，左侧导航支持图标化收起/展开与 Ctrl/⌘ B，窄桌面和移动端自动降级。
