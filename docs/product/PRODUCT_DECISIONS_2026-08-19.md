## 1. 为什么需要单独的决策记录

主档案适合保留完整上下文，但不适合作为每次开发决策的唯一入口。后续重要变化应记录：

```text
旧方案 → 暴露的问题 → 新方案 → 验证结果 → 是否继续保留
```

这份文档不替代主档案，而是记录当前哪些内容已经可以作为执行约束，哪些仍然是待验证假设。

## 2. 决策状态

| 状态 | 含义 |
|---|---|
| `stable` | 已经成为当前执行约束，除非有新证据，不轻易改变 |
| `experiment` | 正在实现或验证，允许根据反馈调整 |
| `proposed` | 已提出但尚未进入实现 |
| `deprecated` | 已明确废弃，保留记录以解释演进 |
| `blocked` | 需要外部条件、用户反馈或权限才能继续 |

## 3. 当前决策

### D-001：MVP 的核心任务是“现实到下一步”

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：第一版围绕 `Capture → Matter → 今日最小行动 → Record → 调整` 展开。
- **原因**：主档案包含多个长期方向，若同时进入第一版，用户无法感知核心价值，工程也会被边界拖散。
- **影响**：关系系统、复杂知识库、完整五行、双向同步和高级 AI 不进入 MVP 核心流程。
- **验证方式**：观察用户是否能在首次使用后 3 分钟内创建 Matter 并确定第一条最小行动。

### D-002：Capture 不自动升级为 Matter

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：只有当 Capture 满足多个现实复杂度条件时，系统才建议升级为 Matter。
- **条件**：持续时间、多个行动、判断取舍、资源消耗、复盘价值，至少满足两项。
- **原因**：Matter 过度泛化会重新制造分类和维护成本。
- **验证方式**：统计 Capture 被用户保留为 Record / Action 的比例，以及用户拒绝创建 Matter 的原因。

### D-003：事实与解释必须分层

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：`Record` 保存事实；`Observation` 保存推断；`Insight / Trajectory` 保存经确认的判断；`Action` 保存下一步行动。
- **原因**：系统和 AI 的解释可能错误，不能把解释永久伪装成事实。
- **验证方式**：每个判断都能回到 `evidence_ids`，并可被用户修改或推翻。

### D-004：五行默认隐藏

- **状态**：`experiment`
- **日期**：2026-08-19
- **决策**：底层保留五行 Stage，普通 UI 默认显示自然语言阶段；用户主动打开后才显示五行名称。
- **原因**：五行是内部过程模型，不应成为用户学习产品的前置门槛。
- **验证方式**：新用户是否能在不理解五行的情况下完成完整闭环；老用户是否仍能获得足够的过程表达能力。

### D-005：IndexedDB 是 MVP 本地主事实源

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：IndexedDB 保存本地长期实体、Record 和 Mutation Log；D1 与 Markdown 是镜像 / 外部工作区，不是第一版事实源。
- **原因**：避免浏览器数据库、云端数据库和 Markdown 同时成为主数据库。
- **验证方式**：断网运行、刷新恢复、导出重导入和冲突测试均不丢失核心历史。

### D-006：关系系统不进入 MVP 主流程

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：MVP 只支持个人系统；Person 作为上下文关联，Shared Space 和多人编辑延后。
- **原因**：多人权限、隐私、共享范围和冲突会显著增加领域复杂度；在个人模型未验证前不应提前承载。
- **进入条件**：权限模型、共享 Record 边界、撤回共享、导出删除和冲突审计全部明确。

### D-007：Calmy 定位为 Attention OS

- **状态**：`stable`
- **日期**：2026-08-29
- **旧方案**：以任务、模块和 Dashboard 组织首页与产品能力。
- **当前决策**：Calmy 首先保护注意力并把用户送回现实；Today 收敛为“现在 / 思考 / 轨迹”的 Attention Surface，四个主入口保持不变。
- **原因**：信息和 AI 生成能力不再稀缺，注意力、主体判断和现实行动才是有限资源。
- **影响范围**：产品 / UI / 指标。
- **验证方式**：用户在 10 秒内能说出当前现实行动；系统内停留不因新设计增长为目标。

### D-008：身体是轻量事实，不是量化指标

- **状态**：`stable`
- **日期**：2026-08-29
- **当前决策**：Today/Review 可提供可跳过的“很好 / 正常 / 疲惫 / 明显不舒服”，用于调整行动粒度和文案；不建立 Health Dashboard、评分、连续打卡或医疗判断。
- **原因**：身体应被看见，但不应成为新的系统维护和生产力考核对象。
- **影响范围**：产品 / UI / AI / 隐私。
- **验证方式**：不填写身体状态仍能完成核心流程；疲惫场景优先出现降载与休息，而非失败提示。

### D-009：Self、Experience 和 Memory 不建立第二套事实源

- **状态**：`stable`
- **日期**：2026-08-29
- **当前决策**：Self 由当前用户、偏好和主动确认原则表达；Experience 使用 Record 的用户语言视图；Memory 是 Fact、Reflection、AI Inference、Preference、Principle 的分层视图。它们复用现有 Repository、Record、Observation、Insight、Seed 和 Resource。
- **原因**：新理念不应复制实体、历史和同步状态。
- **影响范围**：领域 / 数据 / AI / 同步。
- **验证方式**：任何新视图都能回到现有稳定 ID 和来源；导出、同步和搜索不产生重复对象。

### D-010：AI 帮助判断但不替人判断

- **状态**：`stable`
- **日期**：2026-08-29
- **当前决策**：AI 可以过滤、连接、解释、推演和准备数字材料，但不能成为最终价值判断者。AI Inference 永远不能自动升级为 Fact、Preference 或 Principle；用户可查看、修改、否认和删除 AI 记忆。
- **原因**：长期替用户决策会削弱主体性，并让过去数据限制未来变化。
- **影响范围**：AI / 数据 / UI / 隐私。
- **验证方式**：每个 AI 判断都有证据、置信度和确认状态；拒绝或删除后不再作为已确认事实参与建议。

### D-011：结束和放下是一等能力

- **状态**：`stable`
- **日期**：2026-08-29
- **当前决策**：暂停、跳过、归档、再见、无需继续和不记录与“创建、获得、完成”同等重要；Trajectory 允许停滞、回退、绕路、失去、恢复和重启。
- **原因**：只积累不退出会让系统越来越满，并把真实人生误写成单向成长曲线。
- **影响范围**：产品 / 领域 / UI / 指标。
- **验证方式**：用户能够结束 Matter/Cycle/Action 而不收到失败评价；所有 Trajectory 判断可回到证据并被推翻。

### D-012：学习只服务于解决真实问题

- **状态**：`stable`
- **日期**：2026-09-07
- **旧方案**：把“学习”或“更自律”作为可独立追求的 Matter，用学习时长、连续天数、课程完成量、答题数或打卡衡量进展。
- **暴露的问题**：过程指标与现实结果脱节，会制造无尽课程、收藏和自我考核，让用户为系统维持“努力”的形象。
- **当前决策**：学习是 Matter 内部填补信息或能力缺口的按需行动，不是默认独立目标。设计统一使用“现实问题 → 期望变化/证据 → 当前缺口 → 最小必要学习 → 立即应用/验证 → 现实反馈 → 继续、改法或停止”闭环。
- **边界**：“问题”包括用户愿意承担的实际困难、关系张力、创作命题、好奇问题或探索假设，不等于狭窄功利任务。如果暂时不需要行动，内容可保留为 Seed/Resource，不进入 Today；纯粹休息、欣赏和生活本身也不必被伪装成学习或解题。
- **度量规则**：默认看问题是否更清楚、是否产生可验证产物、新知是否被使用、现实是否返回反馈，以及用户是否知道何时已经足够。时长、频次、正确率、连续天数只允许作为用户主动选择的诊断信号或外部要求，不独立成为产品成功指标。
- **影响范围**：产品 / 领域 / UI / AI / Flow / LIMS / 报告 / 指标 / 验收。
- **验证方式**：用户能在 3 分钟内从一个现实问题得到一个可执行的学习或查证行动，并能说出它将用在哪里、什么证据表示足够；未完成连续学习不会触发失败评价。

### D-013：飞书多维表格作为可配置外部数据源

- **状态**：`experiment`
- **日期**：2026-09-19
- **旧方案**：所有用户数据只通过 Calmy 本地 Repository 管理，外部云端仅作为同步镜像。
- **暴露的问题**：用户已经在飞书多维表格中维护项目、任务、成员和周报；为了使用 Calmy 再复制一套数据，会增加录入和维护成本。
- **当前决策**：增加飞书多维表格适配层，让 Calmy 可以作为飞书数据的自定义表格、看板、Today 和复盘前端。第一阶段使用 `tenant_access_token` 连接单一用户授权的 Base；不在浏览器暴露 App Secret。首版页面按已校准字段名读取并兼容任务标题别名，字段 ID 映射与任意改名、类型变化的自动兼容由 OW-19 继续推进。
- **边界**：D-005 的 IndexedDB 本地主事实源在真实数据往返、权限、错误恢复和用户试用完成前继续有效；飞书适配不能静默替换本地 Repository，也不建立第二套同步事实源。跨租户多人使用需另行增加 OAuth、Token 刷新、租户隔离和权限审计。
- **影响范围**：数据 / UI / 后端 / 授权 / 同步。
- **验证方式**：使用现有“项目管理甘特图” Base 完成项目、任务和周报的 schema 读取；Calmy 能读取任务、创建任务、修改任务状态，飞书外部修改不会破坏页面；错误和未配置状态可见；完整闭环通过后再决定是否升级为主数据源。

### D-015：核心页面显式飞书模式与自动刷新

- **状态**：accepted（2026-09-19，用户要求继续打通核心页面）。
- **决策**：Today、Capture、事项与事项看板提供共享的本地 / 飞书来源切换；默认保留本地，用户选定飞书后读取同一 Base。飞书 Capture 明确是创建任务，不自动把通用原文转成任务；本地 Capture 保持原样。
- **写入边界**：飞书任务直接经 Worker 写回，不复制成 IndexedDB Action/Matter。今日安排只保存工作区隔离的记录 ID 引用，不改截止日期。飞书项目、周报、成员暂只读；Review 和旧工具模块仍为本地能力。
- **刷新与验证**：活跃飞书页面每 15 秒检查更新，聚焦 / 恢复可见 / 网络恢复时读取；无事件推送承诺。任务看板支持拖拽到 schema 中的状态列，写回成功后再刷新；表格视图和右侧详情只操作原始飞书记录。保存失败保留输入且不显示成功、不自动重试写操作。保留旧数据，部署由用户完成，线上写回单独验收。
- **性能优化**：拖拽写回得到飞书确认后立即更新当前卡片，完整读取放到后台；后续按受影响表、缓存时效和 schema 变化减少请求。结果未知时不移动或重复创建，提示用户核对飞书。
- **字段兼容**：首次按名称匹配字段，按工作区记录字段 ID，后续通过 schema 解析当前名称；删除、类型变化停用相应写入并显示原因。状态列来自 schema，未知状态也必须可见。

### D-016：建立飞书官方能力同步清单

- **状态**：accepted（2026-09-19，用户要求）。
- **决策**：将飞书多维表格官方能力按数据模型、视图、协作、授权、同步和自动化分类登记，持续写入 [飞书官方能力同步清单](FEISHU_OFFICIAL_CAPABILITY_CHECKLIST_2026-09-19.md)。
- **范围**：目标是逐步兼容用户当前 Base 与飞书多维表格相关能力，不承诺一次性复制飞书全部产品，也不复制官方品牌资产或内部实现。
- **完成规则**：官方能力必须经过 API、权限、真实 Base、失败恢复和用户体验验收后，才从“待实现”标记为“已实现”；未知字段和未知状态不可静默丢失。

### D-017：设置与同步只有一个界面，所有页面复用同一视觉基础

- **状态**：`accepted`
- **日期**：2026-09-19
- **暴露的问题**：普通 React 设置页与完整 Vault / 实体迁移页功能重叠，用户需要判断哪个才是真正的设置入口；React 与兼容页的卡片、表单、主按钮和状态层级也出现了不一致。
- **决策**：`/app/admin` 作为唯一主入口，直接展示用户选定的完整设置与同步界面；`/app/admin/advanced` 只保留为兼容地址并复用该界面。通过共享设计令牌统一所有 React 页面及完整管理页的颜色、表单焦点、卡片层级、主按钮、标签页、空状态、动效与窄屏规则。
- **边界**：此决策不删除 Vault、同步或实体迁移能力，不改变数据事实源、同步协议或旧书签。Vue 兼容层退出仍由 OW-06 的真实路由回归和回滚方案决定。
- **验证方式**：两个地址显示同一组设置能力；核心四页、扩展页面与管理页在桌面和窄屏下保留清晰的标题、主操作、保存状态、键盘焦点和退出路径；构建与静态无障碍回归通过。

### D-014：飞书生活工作台与减少日常维护

- **状态**：`proposed`
- **日期**：2026-09-19
- **暴露的问题**：用户认为系统维护繁琐；目前 FeishuPage 为独立二级入口，Today 等核心页面仍使用本地数据，不能仅凭飞书接通就视为新系统完成。
- **规划建议**：飞书工作区以现有 Base 保存项目、任务和周报；Calmy 提供“今天 / 项目 / 回顾”与全局快速新建，默认只展示必要字段。个人今日选择和界面设置只保存记录引用，派生概况不另建可编辑数据。具体见 [飞书生活工作台规划](FEISHU_LIFE_WORKSPACE_PLAN_2026-09-19.md)。
- **边界**：规划不自动改写现行四入口、D-005 本地主事实源或历史数据；字段 ID 映射、核心页面来源统一和真实写回验收完成后，才评估启用飞书模式默认入口。成员表不等于登录账号，当前共享密码接口不开放为团队账号系统。
- **实施顺序**：稳定映射与线上读写 → 今天与快速录入 → 项目回顾与缓存 → 经试用后推进跨设备和多人能力；活跃工程任务统一由 OW-19 管理。
- **验证方式**：用户能减少重复录入和切换；标题必填即可创建，无日期也能选入今天；飞书字段改名与状态增加不破坏已建立的映射；保存失败不显示成功。以真实生活收益和维护耗时决定是否继续。

## 4. 当前实验假设

### H-001：用户需要“可以放下什么”，而不只是“要做什么”

- **状态**：`experiment`
- **验证**：观察 Today 中 `let_go` 被使用的频率，以及用户是否认为它减少了压力。

### H-002：用户愿意记录负向现实，但不愿意被系统评价

- **状态**：`experiment`
- **验证**：比较自由记录、标签记录和 AI 建议三种方式的接受率与修改率。

### H-003：最小必要行动比完整计划更适合低能量场景

- **状态**：`experiment`
- **验证**：在“疲惫 / 很差”状态下观察用户是否更愿意完成一个小行动，而不是直接退出。

## 5. 已废弃方向

| 旧方向 | 暴露的问题 | 当前替代 |
|---|---|---|
| 功能模块平铺 | 入口越来越多，维护成本上升 | 少数核心对象 + Relation + View |
| 任务作为唯一第一入口 | 不能表达长期现实与关系上下文 | Matter 为主体，Today 为行动视图 |
| 人物作为唯一入口 | 知识、行动和个人事项不总能挂到他人 | Person 是 Context，不是唯一入口 |
| 一件事只走一次五行 | 长期事项无法表达多轮迭代 | Matter + 多轮 Cycle |
| 只记录完成与成长 | 得不到真实的回退、损耗和逃避信息 | Record + Trajectory + 负向历史 |
| AI 独立聊天页 | 容易变成上下文不足的套壳 | AI 作为理解层，嵌入 Capture / Review |
| 第一版实时双向同步 | 冲突与数据所有权风险过高 | 先导入导出，再增量，再双向 |
| 学习或自律本身作为目标 | 时长、打卡和内容消费会代替真实结果 | 现实问题 + 最小必要学习 + 当下应用验证 |

## 7. 维护规则

- 追加，不覆盖；修订时保留旧方案和原因。
- 原则、当前决策、实验假设和废弃方向不得混写成同一种语气。
- 新功能先检查是否违反已有 `stable` 决策。
- 发生冲突时，优先以现实反馈和用户可验证证据为准。
- 每个 `experiment` 至少写明验证方式和复查时间。
- 能进入开发的决策，必须能在 [MVP 验证与测试计划](reference/Calmy_MVP验证与测试计划_2026-08-19.md) 中找到对应验收场景。
- 任何重要变更都应同步回 [MVP 范围](reference/Calmy_MVP产品范围与不做清单_2026-08-19.md)、[领域模型](reference/Calmy_领域模型与状态机_2026-08-19.md)、[用户流程](reference/Calmy_核心用户流程与界面规格_2026-08-19.md) 或 [AI / 同步协议](reference/Calmy_AI行为规则与开放数据同步协议_2026-08-19.md)。
