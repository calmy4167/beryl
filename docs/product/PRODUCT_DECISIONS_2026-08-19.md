# Calmy 产品决策记录与演进规则

> 用于把长期原则、当前决策、实验假设和已废弃方案分开。  
> 版本：v0.1 · 日期：2026-08-19

验证入口：[路线图与验收](ROADMAP_AND_ACCEPTANCE_2026-08-22.md) · 当前未完成工作：[OPEN_WORK](OPEN_WORK.md)

## 1. 为什么需要单独的决策记录

主档案适合保留完整上下文，但不适合作为每次开发决策的唯一入口。后续重要变化应记录：

```text
旧方案 → 暴露的问题 → 新方案 → 验证结果 → 是否继续保留
```

这份文档不替代主档案，而是记录当前哪些内容已经可以作为执行约束，哪些仍然是待验证假设。

## 2. 决策状态

| 状态 | 含义 |
|---|---|
| `stable` | 已经成为当前执行约束，除非有新证据，不轻易改变 |
| `experiment` | 正在实现或验证，允许根据反馈调整 |
| `proposed` | 已提出但尚未进入实现 |
| `deprecated` | 已明确废弃，保留记录以解释演进 |
| `blocked` | 需要外部条件、用户反馈或权限才能继续 |

## 3. 当前决策

### D-001：MVP 的核心任务是“现实到下一步”

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：第一版围绕 `Capture → Matter → 今日最小行动 → Record → 调整` 展开。
- **原因**：主档案包含多个长期方向，若同时进入第一版，用户无法感知核心价值，工程也会被边界拖散。
- **影响**：关系系统、复杂知识库、完整五行、双向同步和高级 AI 不进入 MVP 核心流程。
- **验证方式**：观察用户是否能在首次使用后 3 分钟内创建 Matter 并确定第一条最小行动。

### D-002：Capture 不自动升级为 Matter

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：只有当 Capture 满足多个现实复杂度条件时，系统才建议升级为 Matter。
- **条件**：持续时间、多个行动、判断取舍、资源消耗、复盘价值，至少满足两项。
- **原因**：Matter 过度泛化会重新制造分类和维护成本。
- **验证方式**：统计 Capture 被用户保留为 Record / Action 的比例，以及用户拒绝创建 Matter 的原因。

### D-003：事实与解释必须分层

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：`Record` 保存事实；`Observation` 保存推断；`Insight / Trajectory` 保存经确认的判断；`Action` 保存下一步行动。
- **原因**：系统和 AI 的解释可能错误，不能把解释永久伪装成事实。
- **验证方式**：每个判断都能回到 `evidence_ids`，并可被用户修改或推翻。

### D-004：五行默认隐藏

- **状态**：`experiment`
- **日期**：2026-08-19
- **决策**：底层保留五行 Stage，普通 UI 默认显示自然语言阶段；用户主动打开后才显示五行名称。
- **原因**：五行是内部过程模型，不应成为用户学习产品的前置门槛。
- **验证方式**：新用户是否能在不理解五行的情况下完成完整闭环；老用户是否仍能获得足够的过程表达能力。

### D-005：IndexedDB 是 MVP 本地主事实源

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：IndexedDB 保存本地长期实体、Record 和 Mutation Log；D1 与 Markdown 是镜像 / 外部工作区，不是第一版事实源。
- **原因**：避免浏览器数据库、云端数据库和 Markdown 同时成为主数据库。
- **验证方式**：断网运行、刷新恢复、导出重导入和冲突测试均不丢失核心历史。

### D-006：关系系统不进入 MVP 主流程

- **状态**：`stable`
- **日期**：2026-08-19
- **决策**：MVP 只支持个人系统；Person 作为上下文关联，Shared Space 和多人编辑延后。
- **原因**：多人权限、隐私、共享范围和冲突会显著增加领域复杂度；在个人模型未验证前不应提前承载。
- **进入条件**：权限模型、共享 Record 边界、撤回共享、导出删除和冲突审计全部明确。

## 4. 当前实验假设

### H-001：用户需要“可以放下什么”，而不只是“要做什么”

- **状态**：`experiment`
- **验证**：观察 Today 中 `let_go` 被使用的频率，以及用户是否认为它减少了压力。

### H-002：用户愿意记录负向现实，但不愿意被系统评价

- **状态**：`experiment`
- **验证**：比较自由记录、标签记录和 AI 建议三种方式的接受率与修改率。

### H-003：最小必要行动比完整计划更适合低能量场景

- **状态**：`experiment`
- **验证**：在“疲惫 / 很差”状态下观察用户是否更愿意完成一个小行动，而不是直接退出。

## 5. 已废弃方向

| 旧方向 | 暴露的问题 | 当前替代 |
|---|---|---|
| 功能模块平铺 | 入口越来越多，维护成本上升 | 少数核心对象 + Relation + View |
| 任务作为唯一第一入口 | 不能表达长期现实与关系上下文 | Matter 为主体，Today 为行动视图 |
| 人物作为唯一入口 | 知识、行动和个人事项不总能挂到他人 | Person 是 Context，不是唯一入口 |
| 一件事只走一次五行 | 长期事项无法表达多轮迭代 | Matter + 多轮 Cycle |
| 只记录完成与成长 | 得不到真实的回退、损耗和逃避信息 | Record + Trajectory + 负向历史 |
| AI 独立聊天页 | 容易变成上下文不足的套壳 | AI 作为理解层，嵌入 Capture / Review |
| 第一版实时双向同步 | 冲突与数据所有权风险过高 | 先导入导出，再增量，再双向 |

## 7. 维护规则

- 追加，不覆盖；修订时保留旧方案和原因。
- 原则、当前决策、实验假设和废弃方向不得混写成同一种语气。
- 新功能先检查是否违反已有 `stable` 决策。
- 发生冲突时，优先以现实反馈和用户可验证证据为准。
- 每个 `experiment` 至少写明验证方式和复查时间。
- 能进入开发的决策，必须能在 [MVP 验证与测试计划](reference/Calmy_MVP验证与测试计划_2026-08-19.md) 中找到对应验收场景。
- 任何重要变更都应同步回 [MVP 范围](reference/Calmy_MVP产品范围与不做清单_2026-08-19.md)、[领域模型](reference/Calmy_领域模型与状态机_2026-08-19.md)、[用户流程](reference/Calmy_核心用户流程与界面规格_2026-08-19.md) 或 [AI / 同步协议](reference/Calmy_AI行为规则与开放数据同步协议_2026-08-19.md)。
